# E4f 本地积分快递冷备份恢复

分支：`积分商城`。负责人本轮确认尚无 HTTPS 测试服务器/域名，先完成本地恢复演练和部署准备。本轮边界为可重复运行的恢复实验，不新增商城业务规则、页面、API 或数据迁移，不部署外部环境。

## 验收案例与实现

- 显式启用且不接受已有数据目录/连接 URL；从锁定的 PG17.11 二进制创建独立回环实例和随机自有目录，随机凭据不写 Git/报告。
- 走真实 API 建立合成 CONTROLLED 待发、已发（留痕运单更正及加密反馈）、已取消订单，全部迁移在新实例执行。
- 所有连接关闭、源库完整停库后复制整个集群到备份；逐文件长度/SHA-256 校验后复制到另一恢复目录。新目录启动，原源目录保持停止；绝非重连原 schema 或重放空迁移。
- 恢复 API 读取前，对110张表逐行排序内容摘要及行数完全比较，覆盖积分账户/流水、库存/批次/库位/预占消费释放、订单、运单历史归属、反馈、幂等、权限和审计。
- 错误密钥读取原地址/反馈返回500；恢复单独保存在内存的合成密钥副本后，地址、反馈完整历史、来源模式、更正运单和原发货时间保持一致。
- 暂停新兑换及作业时，7个已成功原键恢复；历史原运单和更正运单各拒绝另一订单占用。请求后除认证会话活动时间外所有表逐行内容不变；首发检查订单差异0，无骑手任务，canLaunch=false。
- 正常/校验失败路径只停止和清理本轮自建集群；删除前解析并验证绝对路径，拒绝 `.local` 联接、复制树内联接/特殊文件，不接受外部表空间。

工具及操作见[本地恢复说明](../operations/POINTS-EXPRESS-LOCAL-RECOVERY.md)。报告为忽略的 `.local/express-recovery-report.json`，只含时间、校验数量、总体摘要与结果，无连接 URL、密码、密钥或顾客资料。

## 实际检查

初轮在 Windows pg_ctl 子进程继承捕获管道处超时，已改为启动/停止时关闭捕获管道、输出写自有日志；失败未计通过。随后独立完整恢复通过，最终版本再次完整复验退出码0：110表、1761文件、56,116,894字节一致，7个原键、2项错误密钥读取、2项历史运单防重通过，随机集群清理完成。报告生成于2026-11-04 09:49:54（北京时间），备份复制/恢复/首次逐表核对约10.897秒，仅为本机小样本耗时。

执行项目锁定 Node24.22.1、pnpm10.28.2、PG17.11：

- `npm run build:server` 通过。
- `node --test tests/express-recovery.test.mjs` 两项通过：显式启用/拒绝自定义目标；同长度损坏摘要变化及外部目录联接拒绝。
- `YUMI_LOCAL_RECOVERY=1` 下运行 `node --import tsx scripts/verify-express-recovery.mjs`：独立完整冷备份恢复及业务校验通过。
- `node --env-file=.env --import tsx --test --test-concurrency=1 tests/points-express-gate.integration.test.ts`：三个既有正式门禁 PG 回归全部通过，原本机测试库只使用临时schema并清理。
- 新改脚本/夹具 ESLint、Prettier、根测试 TypeScript 检查通过；`git diff --check`通过。

数据库驱动现有 PG8 查询排队弃用警告仍会出现，不影响本轮结果；未升级锁定依赖或拓展无关改动。
