## 本地复跑与版本清单

使用项目锁定的Node24.22.1、pnpm10.28.2和现有本机PostgreSQL。保留现有.env，不把密码、密钥、token、真实地址写入报告或Git。

1. 运行npm run db:generate、npm run build、npm run lint、npm run typecheck、npm run openapi:export。
2. npm run test:express:release验证本地检查保护；npm run test:express:regression运行打印/地址/兑换/发货/纠错/反馈/检查与重启的44项PG。仅使用127.0.0.1的yumi_test随机schema，不向业务主库造测试单。
3. npm run check:express:release生成只读JSON报告；npm run verify:express:migrations增加临时schema全迁移重放。保存输出到.local/express-release-report.json即可，本地忽略保存。报告只输出布尔门禁、迁移名称/哈希、固定产物路径/哈希、API版本；不输出数据库URL、密钥或小程序API域名。
4. 清单的哈希仅标识当前文件，不证明产物与源码匹配、服务健康或外部验收；本次构建和测试记录需一起保留。小程序清单有完整文件清单且验证当前输出，target=local仍不能通过device条件。
5. 真机包必须使用真实受控HTTPS测试API，按既有build:mini:device/verify:mini:device路径生成。缺少域名/正式身份时不使用示例域名、关闭平台域名校验或开发账号冒充通过。

后台“积分快递首发检查”连接GET /api/v1/admin/redemption-express-readiness，只有本仓运营/负责人可读。页面不接受密钥，不保存人工“验收通过”，没有开启交易或发布按钮，canLaunch始终false。加载/读失败时清理旧结果，失权后不继续显示旧汇总。

小程序构建校验包含独立快递地址页的JS/WXML及页面配置。首发CLI要求当前有效的小程序清单；缺失/过期返回本地检查失败，须重新执行实际构建，而不是手写清单放行。

## 经营与设备验收案例

以下均为**待执行**，不是已经确认的经营规则。每项记录实际执行人、时间、环境/版本、预期/实际结果和脱敏证据，不在文档填写真实姓名、手机号、住址、运单号或平台凭据。

| 场景 | 预期与证据 |
|---|---|
| 正式身份与隐私 | 工具和至少实际可用设备验证登录/失效/换账号；不能查询他人订单/反馈，切后台后旧资料清理；设备覆盖缺口如实记录 |
| 实际兑换 | 已核实商品、规格、积分、配额、批次/库位/效期及寄送范围；报价变化或库存不可用不扣分；网络未知用原键确认同一单 |
| 发货前取消 | 原单一次退分、释放预占和配额；与发货竞争只成功一边；取消后不能打印/发货 |
| 实际打印 | 本单/批量配货单、中文/分页/件数/收件快照可辨；打印前再次校验；配货单不是电子面单，不把预览当打印成功 |
| 实际寄出 | 按原预占批次、库位和件数核对，确认商品完好及承运可达/费用，实际交快递后确认发货；不重复扣积分/出库 |
| 运单与纠错 | 用户看到/复制实际运单；更正只追加历史，原发货时间/库存不变；重复或其他订单历史运单被拒绝 |
| 售后沟通 | 用户说明/补充、运营公开回复/结束、用户重新反馈；准确描述实际处理，登记反馈不等于退款、退货或补寄成功 |
| 断网与失权 | 两端提交响应丢失、刷新/重启后原键核实；旧版本阻断；员工失权不能继续访问/处理 |
| 密钥恢复 | 在隔离恢复环境取得合法密钥副本，解密原地址及反馈；缺密钥时明确失败而非伪造空地址 |

## 备份与恢复演练边界

真正的备份恢复需另行在独立受控环境执行：保护数据库备份与加密密钥、恢复到新目标，先停接单/作业，核对订单/积分流水/库存预占和消费/运单及历史归属/反馈事件/原键。需比较逐笔事实和数量，不只比较表数或HTTP200。明确恢复窗口内已经发生的实物交快递，不删除这些事实来“恢复待发货”。确认可解密原地址/反馈并核实原键后，才记录演练通过。

本轮只重放空schema迁移，以及关闭API/连接池后在同一临时schema重建应用实例；均未恢复备份、未模拟整机断电、未验证密钥外部备份或生产RPO/RTO。生产库不得被开发演练覆盖。恢复目标/备份保留期限由负责人按实际环境确认。

## 匹配部署与暂停/回退顺序

此处是待执行方案，**本轮没有授权或执行生产部署**。

1. 正式身份与生产写门禁完成代码/本地/受控测试验收后，记录具体提交、API/Worker/Web/weapp产物哈希和完整迁移版本；指定值守人，准备隔离恢复及异常手册。
2. 先暂停新兑换及新作业，保留原键核实与已受理单查询；完成独立备份恢复检查，在受控窗口执行兼容迁移，再发布匹配API/Worker、后台和消费者客户端。不得让旧API继续只读原运单而忽略更正历史。
3. 核对探针、当前schema/迁移、加密资料解密、权限、原键、库存/积分不变量和待办。更新小程序体验/审核/发布须在对应平台流程与授权内操作，不由此检查页执行。
4. 对商品/用户/时段采取负责人确认的受控范围；出现数据差异时先暂停相关商品/操作，保留原始事实和未核实请求，按订单核对实物与日志。
5. 回退优先前向修复，应用只能回到兼容已有事实的版本；不得删除新增更正/反馈/运单归属，不将EXPRESS_SHIPPED改为待发货，不恢复旧备份抹去新订单，不自动回补实物或退分。

当前开发开关不能用于以上正式操作；不得通过取消生产/远程拒启校验来“让首发跑通”。

## 监控与值守

检查页实时快照提供本仓待快递发货数/最早待发订单时间、已发货数、未结束反馈数，及订单/原预占、运单历史归属、反馈投影三类差异。数字没有预设业务超时阈值，也没有自动发外部消息；阈值和通知渠道待负责人确认。读取失败代表未知，不代表零异常。

- 订单/预占或运单归属差异：暂停相关发货/新兑换，核对源单、预占、消费/释放流水、原发货及全部更正事实，禁止直接改表填平。
- 未结束反馈和待发积压：运营核查当前队列与实际实物，人工跟进；不能用“结束反馈”掩盖未解决的真实商品问题。
- 401/403、5xx、加密失败、连接/锁等待：按请求号定位脱敏日志、检查当前会话/权限、版本和资源；不向日志补记收件资料或消息全文。
- 日结：抽核积分借贷/取消退分、原预占/实物出库、待发/已发清单、运单更正与未结束反馈，核实备份任务及当班异常记录。真实快递运输进度仍由承运方核实。
