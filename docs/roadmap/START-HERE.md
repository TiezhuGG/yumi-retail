# 开发开工指南

日期：2026-10-26。结论：可以进入S0技术验证与S1工程初始化，不必等待所有商品、设计稿、商户审核和服务器购买完成。开发开始、真实支付可联调、正式上线分别验收。

## 2. 开工时先完成的事

1. 数据库已确定PostgreSQL，开发环境已确定本机Docker Desktop；不再并行维护MySQL实现。
2. 使用Compose隔离开发库与测试库，只绑定回环地址；系统软件安装或重启若出现仍单独说明。
3. 运行最小兼容性验证，记录精确版本。现有Node版本能运行不代表所有Taro/Nest/Prisma组合已验证。
4. 明确第一切片与验收：商品创建→真实入库→API查询→小程序展示。初始化阶段先做启动、迁移、种子、CI，不一次写完全部业务。

Git仓库已存在，无需重复初始化。本地提交、是否推送到远程及仓库可见性在实际协作时明确；无需开工前先创建复杂分支体系。

## 3. 可以并行补充的材料

- 首批3–10个真实商品：名称、规格、单位、图片、售价、条码、是否管理效期、期初数量。资料未到时用明确合成样例，不能直接上线。
- 经营规则：服务小区/楼栋、营业时间、起送与运费、缺货处理、退款权限和联系方式。未确认时按PRD开发默认值配置，不能对外当作正式承诺。
- 员工与配送：仓管、拣货、调度、骑手由谁承担；一个人可有多角色，但数据权限仍分开。
- 经营主体、小程序AppID、管理员、支付商户与绑定状态、域名与备案状态。先提供“有/申请中/没有”等状态，密钥在受控本地配置。
- 品牌图标与图像使用来源；先确认关键页面组件和交互，不必为了全套可编辑Figma稿暂停基础工程。

开工前不用先买生产服务器、订阅付费设计工具或把112项任务逐一描述给Codex。

## 4. 推荐的前两次开发任务

**第一次：S0最小技术验证。** 使用已确认PostgreSQL，先统一文档，然后验证数据库迁移、事务回滚和库存争抢；并验证Taro编译。输出VERSION-MATRIX、运行证据和未验证项。遇到系统软件/账号缺口，完成独立部分并准确说明。

**第二次：S1工程骨架。** 创建consumer-mini/admin-web/ops-mobile/api/worker及共享契约包、环境样例、健康检查、开发数据库、迁移和种子、CI。退出条件是按README能复现启动与检查，不能只交空目录。

随后S2先交付商品/收货入库/库存真实读写，再连接消费者端；仓库移动作业和骑手闭环按任务依赖实现。

## 5. 与Codex协作的最少信息

每次只需说明：这次完成什么、在哪个阶段、如何验收、有哪些新增约束。现有文档和代码直接从工作区读取。不要重复粘贴全套文档、给没有依据的角色修饰词，或要求一次完成整个商业系统。

常规结果应包含可运行产物、实际检查与结果、尚未验证项、演示方法和状态记录更新。某项因真机/账号暂时未验证时，其他已授权且独立的工作继续完成。
