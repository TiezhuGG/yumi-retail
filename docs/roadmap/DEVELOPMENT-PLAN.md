## 1. 执行方式

每次只推进一个可验收业务切片，以“输入→业务结果→异常→证据”作为完成标准。所有资金、库存和权限检查在服务端落实。负责人负责规则、凭据、真实资料与实物验收；Codex负责设计细化、代码、检查和文档。真实设备/账号/仓库操作不能被模拟结果替代。

原 YM-001–086 编号仍可在[原清单](../references/yumi-original.md)追溯；新增编号从087开始。原清单“不开发仓库/骑手系统”的验收条款，已被用户2026-10-25最新要求覆盖。原阶段P0–P9对应下表S0–S9，阶段编号不表示缺陷优先级。

通用：行为符合PRD、接口契约一致、鉴权正确、空错态可理解、必要检查通过、文档同步、无秘密、代码评审完成。页面可打开不代表模块完成。

交易/库存额外：幂等、并发、原子性、状态竞争、补偿、账本、审计。退款额外：金额与数量上限、处理中的占用、未知结果不重退。骑手额外：当前指派权限、弱网、重复动作、送达不扣库存。

阶段检查点：

1. G0：范围和规则基线+版本验证通过，才能批量初始化依赖。
2. G1：商品入库到消费者可见真实联通，才能以此作为交易商品来源。
3. G2：库存/支付竞争测试与受控真实渠道联调通过，才允许对真实用户接单；联调中的授权小额测试单单独记录。
4. G3：仓库出库、骑手送达、退款对账闭环，才可进入限定试运营。
5. G4：部署安全、真机、恢复演练、资料与培训通过，才提交正式上线验收。

## 7. 风险与改期策略

| 风险 | 处理 |
|---|---|
| 商户/审核未准备 | 并行推进，模拟只作开发；真实渠道和发布门禁保持未通过 |
| 负责人时间不足或首次开发 | 根据每周有效投入重排，不按AI生成代码速度承诺日历时间 |
| 无真实商品与仓库资料 | 先合成样例，但上架/入库/出库必须真实运营验收 |
| 范围继续增加 | 记录新增问题、数据影响和依赖，优先放下一版；关键缺陷优先 |
| 兼容性或真机问题 | 在S0发现并记录ADR，避免整个项目安装完才验证 |
| 外部支付/云服务不稳定 | 重试、查单、恢复和人工队列，暂停受影响购买入口 |

加速顺序：减少装饰性图表和营销 → 使用成熟组件 → 固定角色与单仓规则 → 按切片复用。不能通过删掉资金校验、库存事务、退款、权限或恢复验证来加速。
