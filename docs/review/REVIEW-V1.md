# 原始研发计划与 7 张 UI 图评审

评审日期：2026-10-25。依据：实际查看全部 7 张 1448×1086 PNG 图片及原始 yumi.md；同时纳入用户最新补充的“仓库系统、骑手配送系统、暂无生鲜”。

## 1. 总体判断

原清单值得保留：模块化单体、真实 API、库存预占、回调幂等、主动查单、退款不自动回库、备份恢复、试营业验收都在正确方向上。UI 配色、商品卡、购买路径和订单工作台也有良好基础。

现阶段素材可作为视觉与信息结构参考，尚未达到开发定稿。它们是栅格图，缺少可编辑图层、组件参数、响应式规则、接口字段和异常状态；“开箱即用”等图中文字不能作为已验证结论。暂无生鲜后，大量蔬果示例也需换为实际商品。

## 2. 原始文档需要补齐的内容

| 问题 | 影响 | 调整 |
|---|---|---|
| 旧验收要求不新增 WMS、骑手端 | 与用户本轮要求冲突 | 以轻量仓库作业与骑手任务端替换；保留单仓限制 |
| 86 项多为任务描述 | 不足以定义报价、状态、缺货和退款行为 | 先补 PRD 与状态机，再拆实现任务 |
| 商品默认含蔬果和约重 | 对库存/补差款有隐含需求 | 本期按固定 SKU/整数单位；暂无生鲜 |
| 仅写实物/预占库存 | 缺少库位、不可售、效期、损耗、盘点冲突 | 增补批次库位明细、库存流水和盘点作业 |
| 管理员只有笼统角色 | 无法安全开放骑手端 | 增加仓管/拣货/骑手/客服的动作与数据权限 |
| 部分退款缺少规则 | 重复申请可能超退；运费归属不清 | 服务端按原单快照与退款占用计算上限 |
| 对账、补偿未落为数据结构 | 重启或回调延迟可能漏处理 | inbox/outbox、任务租约、异常单与人工处置 |
| 上线资质集中在末期 | 开发完成仍可能无法支付或发布 | 第一天并行确认主体、账号、商户、域名等 |
| 所有任务都要求自动测试 | 对文档/简单样式过重，对关键并发又不够具体 | 按业务风险确定验证，列出交易与库存必测案例 |

## 3. 逐张 UI 评审与修改清单

### board1：登录、工作台、商品、分类

参考：[board1](../references/ui/board1.png)。

- 保留简洁后台布局、商品列表和分类排序。
- 登录页企业微信登录、“记住我”、自助找回密码暂不实现；首期账号由管理员配置，密码重置有审计，不提供默认生产密码。
- 左侧“用户管理、营销中心、财务管理”等不是首版完整模块；移除空入口。财务需求先落为支付/退款对账。
- 工作台的 1,268 单等是示例值，接入后从真实统计生成；待拣、待配、退款、低库存都要可点击定位。
- 商品补充编辑表单、SKU、条码/内部编码、售价、上下架、图片、是否管理效期；上架前必须具备可售库存和完整资料。
- 分类固定最多两级；已有商品的分类禁止直接删除，可停用或迁移。

### board2：库存、订单列表/详情、拣货

参考：[board2](../references/ui/board2.png)。

- “库存管理”的主按钮应为“新建入库单”，不能仍为“新增商品”。
- 可售库存不只等于实物减预占：还需排除不可售、过期及安全库存。表头显示计量单位与仓库。
- 已支付订单不能直接“取消”然后释放库存，应走取消请求、停履约和原路退款。订单不得提供业务删除。
- “再来一单”属于消费者功能，从后台订单操作中移除。
- 拣货页保留逐项数量核对；首版可先用手工输入/扫码枪键盘模式，不能声称已支持手机相机扫码。
- “完成打包”前校验实拣数量、未决缺货、退款和版本；按钮防重复，后端也必须幂等。
- 补充库位、批次、效期、任务领取与锁定；缺货须进入异常队列，不能无声少发。

### board3：配送、售后、经营统计、移动配送

参考：[board3](../references/ui/board3.png)。

- 配送工作台与移动骑手端纳入首版；保留人工分配、接单、开始配送、送达和异常上报。
- 去除实时公里数、定位跟踪等没有数据来源的展示；导航可在后续明确地图接入后增加。
- 增加未接单、拒接/撤回、分配变更、无法送达、误操作纠正等状态。
- 售后“同意退款”只表示审核动作；必须区分退款已受理、处理中、成功、失败、需人工处理。
- 示例销售额 ¥12,680、订单数 1,268、客单价 ¥32.6 若属同一口径并不一致：12,680÷1,268=10。重新定义时间区间与分母。
- 普通骑手不得浏览全部订单、其他骑手详情或顾客历史资料。

### board4：设置、首页配置、日志、权限

参考：[board4](../references/ui/board4.png)。

- 店铺设置保留；明确营业暂停、截单、起送、配送费、服务楼栋和客服时间。
- 图片写“收货 24 小时内联系客服”只能当示意，不能直接当对外售后限制；正式文案需结合经营品类与适用规则核验。
- 首页配置首期仅做推荐商品与静态横幅，移除“满99减20”、领券入口和自由搭建器。
- 操作日志保留并增加失败结果、原因、请求编号和变更字段；不写完整电话、地址、凭据。
- 权限首期使用固定角色与权限点，保留账号分配功能，不开发复杂权限设计器。
- 超级管理员、退款权限和权限修改均必须后端校验；禁止删除最后一个有效管理员。

### mini1：首页、分类、搜索、详情、购物车

参考：[mini1](../references/ui/mini1.png)。

- 保留四 Tab：首页、分类、购物车、我的；详情/搜索不强行显示 Tab。
- 首页改为固定服务小区+营业状态，无须索取定位权限才能浏览；去除 30 分钟承诺。
- 蔬果卡片替换为实际定量商品；详情明确规格、单位、产地/生产信息等实际适用字段。
- 原价划线、月售、折扣和“已优惠”暂不展示，避免引入无来源的促销和销量。
- 不放置伪造的小程序右上角胶囊、系统时间或手机外框；开发使用平台真实区域。
- 购物车的已选示例行合计 9+16.8+5.9=31.7，与图中合计及优惠信息需重新统一。
- 增加无商品、失效商品、下架、限购/库存不足、快速连续加减、报价变化等状态。

### mini2：确认订单、支付结果、地址、我的

参考：[mini2](../references/ui/mini2.png)。

- 金额示例错误：31.7+3−3=31.7，不能显示实付28.7。首版无优惠时统一演示为商品31.7+运费3=34.7。
- 去除预约时段选择；首期展示营业与配送说明，并由服务端决定能否接单。
- 支付结果必须有“确认中”，前端调起支付成功也要等待业务查询确认。
- 地址限制在已配置小区/楼栋，不能像图中允许任意其他小区。禁止只靠前端判断范围。
- 楼栋/单元可配置，房号按字符串验证；联系手机号是送货资料，不强制依赖微信手机号授权。
- 我的页移除积分、优惠券、收藏、反馈等未实施入口；保留订单、地址、客服、商家信息和隐私入口。

### mini3：订单列表/详情、退款、商家、帮助

参考：[mini3](../references/ui/mini3.png)。

- 保留订单进度、商品快照、联系商家和退款入口。
- 配送中不展示实时位置或无依据的准确到达时刻。顾客不可在配送中直接修改地址。
- 退款金额由服务端计算，考虑原单运费与已退/占用金额，不按当前商品售价简单相加。
- 删单、再来一单、关注、评分、月售、自动发票入口暂缓。
- 商家证照必须替换为真实材料，示意证件、电话和评分不得对外发布。
- 订单详情的“确认收货”和骑手送达应统一语义：首版由骑手送达作为履约完成事件；消费者可反馈未收到，无须第二套重复库存操作。
- 补充退款进度页、拒绝原因、退款处理中与失败后的查询入口。

## 4. 页面数量与编号纠正

原计划称“15 个用户页、14 个后台页”。实际素材含 15 个消费者主画面、16 个后台大面板，其中一个是多个骑手移动画面的组合。图片面板数不等于应用路由数。

本基线保留 C01–C15 主编号；补 C16 退款详情、C17 隐私与协议；后台按 A01–A16 重新明确；仓库作业 W01–W06、骑手 R01–R04 单独编号。部分页面是抽屉或同一路由的子状态，不要求全部开发为独立页面。以 [UI 规格](../design/UI-SPEC-V1.md) 为准。

## 5. 设计交付到可开发的条件

每页需要：路由/入口、角色、真实字段、操作权限、状态矩阵、加载与空错态、表单校验、按钮禁用条件、关联接口、测试案例。交易页金额必须来自同一组可计算样例。图库和图标注明来源，可编辑设计稿或组件实现均需版本化。

建议先打磨三组关键页面：商品与入库 → 购物车/确认单/支付 → 仓库拣货/骑手任务。其他页面沿用确认后的组件规则，避免一次重画全套后再返工。
